# 面试官问：订单系统使用MQ高并发场景下（峰值 TPS 10 万 +）如何保证消息只被消费一次？
- https://mp.weixin.qq.com/s/WJJJzMczaGF3XYo_8UbNnQ


当消息队列出现大量消息堆积时，需从**紧急恢复**和**根源优化**两方面入手，既要快速消耗堆积消息，也要避免问题再次发生。以下是具体处理方案：


### 一、紧急处理：快速消耗堆积消息
#### 1. 临时扩容消费者（核心手段）
- **水平扩容**：临时增加消费者实例数量（如从3台扩到20台），利用消息队列的“分片/分区负载均衡”特性，让更多消费者并行消费。  
  - 注意：确保消费者分组（如 RocketMQ 的 `ConsumerGroup`、Kafka 的 `Consumer Group`）配置正确，新实例能加入分组并分配分区。  
  - 极端情况：若消息堆积量极大（如百万级），可临时启动“消费集群”（如用 Kubernetes 快速扩容 Pod），优先消耗堆积消息。

- **优化消费并行度**：  
  - 单个消费者实例内增加消费线程数（如 RocketMQ 的 `setConsumeThreadMin`/`setMax`，Kafka 的 `max.poll.records` 调大），提高单实例处理能力。  
  - 例：Kafka 消费者通过 `max.poll.records=1000`（默认500）让每次拉取更多消息，减少网络交互开销。


#### 2. 降级非核心逻辑，优先处理消息
- 临时注释消费者代码中的非核心逻辑（如日志打印、非关键数据库操作、第三方接口调用），只保留“必要的业务处理”，减少单条消息的处理耗时。  
- 例：原消费逻辑需调用3个外部接口，临时只调用1个核心接口，其他接口后续通过补偿任务处理。


#### 3. 跳过无效消息，避免阻塞
- 若堆积消息中存在格式错误、过期数据（如超时未处理的订单），可在消费逻辑中增加过滤条件，直接跳过无效消息，避免卡在错误消息上。  
- 例：通过消息的 `timestamp` 判断，超过24小时的消息直接标记为“处理完成”，不执行业务逻辑。


#### 4. 消息迁移与分流
- 若原队列持续有新消息写入，可临时创建“堆积消息专用队列”，将历史堆积消息迁移到新队列，用单独的消费者集群处理，原队列保留处理新消息。  
  - 实现方式：  
    - RocketMQ：通过 `admin.consumerMessage` 批量拉取堆积消息，重新发送到新 Topic；  
    - Kafka：通过 `kafka-console-consumer` 消费堆积分区消息，转发到新 Topic。


### 二、根源优化：避免再次堆积
#### 1. 优化消费速度（核心）
- **减少单条消息处理耗时**：  
  - 分析消费逻辑瓶颈（如慢SQL、频繁IO），优化代码（如加索引、批量操作数据库、缓存热点数据）。  
  - 例：将“单条消息插入数据库”改为“批量插入”（每100条消息执行一次 `batchInsert`）。  
- **异步化处理**：将非实时逻辑（如统计、通知）异步化，消费主线程只处理核心业务，其他逻辑通过线程池或另一个消息队列异步处理。  


#### 2. 控制生产速度，削峰填谷
- 若消息生产者（如上游服务）发送速度远大于消费速度，需限制生产速率：  
  - 上游服务引入限流（如 Guava RateLimiter），控制每秒发送消息量；  
  - 利用消息队列的“流量控制”特性（如 Kafka 的 `producer.metrics` 监控，超过阈值时暂停生产）。  
- 对突发流量（如秒杀、活动），提前扩容消费者，或通过“延迟队列”缓冲（如 RocketMQ 的延迟级别），避免瞬间压垮消费端。


#### 3. 扩容消息队列存储与分区
- **增加分区/队列数量**：消息队列的并行消费能力依赖分区数（Kafka）或队列数（RocketMQ），分区越多，可分配的消费者实例越多（单个分区只能被同组内一个消费者消费）。  
  - 例：Kafka 某个 Topic 原分区数为4，最多只能被4个消费者并行消费，扩容到16个分区后，可支持16个消费者并行处理。  
- **优化存储配置**：若消息堆积导致磁盘空间不足，需扩容磁盘，或配置自动清理策略（如保留最近7天的消息，过期自动删除）。


#### 4. 完善监控与告警
- 实时监控消息队列关键指标，设置告警阈值：  
  - 堆积消息数（如超过10万条触发告警）；  
  - 消费延迟（如消息从生产到消费的平均延迟超过5分钟）；  
  - 消费者状态（如消费线程阻塞、实例宕机）。  
- 工具推荐：Prometheus + Grafana 监控（结合 RocketMQ-Exporter、Kafka-Exporter），告警通过 AlertManager 发送到钉钉/邮件。


#### 5. 容错与重试机制优化
- 避免消费失败导致消息反复重试，进而阻塞队列：  
  - 对 transient 错误（如网络波动），设置有限重试次数（如3次），超过后进入死信队列（DLQ），人工介入处理；  
  - 对 permanent 错误（如消息格式错误），直接拒绝并记录到死信队列，不重试。  


### 三、案例：某电商平台消息堆积处理
1. **现象**：订单支付消息队列堆积50万条，消费延迟达2小时，导致下游物流系统无法及时发货。  
2. **紧急处理**：  
   - 临时扩容20个消费者实例，将消费线程数从5调至20；  
   - 关闭消费者中的“物流短信通知”逻辑（非核心），只处理“订单状态更新”；  
   - 将3天前的过期订单消息直接跳过。  
3. **3小时后**：堆积消息消耗完毕，恢复正常延迟（<10秒）。  
4. **根源优化**：  
   - 订单 Topic 分区数从8扩容到32，支持更多消费者并行；  
   - 消费逻辑中数据库操作改为批量提交，单条消息处理耗时从200ms 降至50ms；  
   - 上游支付服务增加限流，峰值 TPS 控制在消费者处理能力内（如2000 TPS）；  
   - 配置监控告警：堆积数>1万条或延迟>5分钟时，自动通知运维扩容。  


### 总结
消息堆积处理的核心逻辑是：**“先通过临时扩容和降级快速消峰，再通过优化消费速度、控制生产速率、完善监控避免复发”**。关键在于提前做好容量规划和监控，避免堆积到“不可收拾”的地步。

# 如何实际操作
针对 Kafka 消息堆积的场景，以下是具体的操作命令和步骤，涵盖**监控堆积、临时扩容、消息迁移、消费速率调整**等关键环节：


### 一、查看消息堆积情况（关键指标监控）
首先需确认堆积的具体分区、消息量及消费延迟，使用 Kafka 自带工具或监控命令：

#### 1. 查看 Topic 各分区的消息总量与消费偏移量
```bash
# 语法：kafka-consumer-groups.sh --bootstrap-server <broker地址> --describe --group <消费组名>
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group order-consumer-group
```
**输出解读**：
- `CURRENT-OFFSET`：消费者当前已消费到的偏移量  
- `LOG-END-OFFSET`：分区最新消息的偏移量  
- **堆积量 = LOG-END-OFFSET - CURRENT-OFFSET**（数值越大，堆积越严重）  
- `LAG`：即堆积量（部分版本直接显示）

示例输出（某分区堆积 10 万条）：
```
TOPIC           PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG        CONSUMER-ID                                       HOST            CLIENT-ID
order-topic     0          50000           150000          100000     consumer-order-1-xxx                             /192.168.1.100  consumer-order-1
```


#### 2. 查看 Topic 分区数（判断是否可通过扩容分区提升并行度）
```bash
# 语法：kafka-topics.sh --bootstrap-server <broker地址> --describe --topic <主题名>
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic order-topic
```
输出中 `PartitionCount` 即为分区数，若分区数过少（如 < 消费者实例数），需扩容分区。


### 二、临时扩容消费者（快速提升消费能力）
#### 1. 增加消费者实例
直接启动新的消费者进程，加入同一消费组（`group.id` 相同），Kafka 会自动将分区重新分配给新实例：
```bash
# 示例：启动一个新的消费者实例（后台运行）
nohup kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic order-topic \
  --group order-consumer-group \
  --from-beginning > /dev/null 2>&1 &
```
- 注意：消费者实例数 **不应超过分区数**（多余实例会空闲，因为一个分区只能被同组内一个消费者消费）。


#### 2. 调整单个消费者的拉取参数（提高单实例吞吐量）
修改消费者配置文件（如 `consumer.properties`），或启动时指定参数：
```bash
# 单次拉取最大消息数（默认500，可增至1000-2000，根据内存调整）
--max-poll-records 2000

# 拉取请求超时时间（默认5000ms，若消息体大，可增至10000ms）
--fetch-max-wait-ms 10000

# 单次拉取的最大字节数（默认5242880字节=5MB，可增至10MB）
--fetch-max-bytes 10485760
```
示例：启动一个高吞吐量的消费者：
```bash
kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic order-topic \
  --group order-consumer-group \
  --max-poll-records 2000 \
  --fetch-max-bytes 10485760
```


### 三、扩容 Topic 分区（提升并行消费上限）
若原分区数过少（如 4 个分区，无法支持 10 个消费者并行），需扩容分区：
```bash
# 语法：kafka-topics.sh --bootstrap-server <broker地址> --alter --topic <主题名> --partitions <新分区数>
kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic order-topic --partitions 16
```
- 注意：  
  1. 分区数**只能增加，不能减少**；  
  2. 扩容后需重启消费者，让消费组重新分配分区；  
  3. 新分区的消息分配依赖生产者的 `partitioner.class` 策略（默认按 key 哈希，可能导致数据分布不均，建议后续优化分区策略）。


### 四、迁移堆积消息到临时 Topic（分流处理）
若原 Topic 持续有新消息写入，可将历史堆积消息迁移到临时 Topic，用单独的消费者集群处理：

#### 1. 创建临时 Topic（用于存储堆积消息）
```bash
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create \
  --topic order-topic-backlog \
  --partitions 16 \
  --replication-factor 3
```

#### 2. 消费原 Topic 的堆积消息，转发到临时 Topic
使用 `kafka-console-consumer` 消费原 Topic 的历史消息，通过管道发送到 `kafka-console-producer` 写入临时 Topic：
```bash
# 消费原 Topic 从起始位置开始的消息，转发到临时 Topic
kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic order-topic \
  --from-beginning \
  --max-messages 1000000  # 限制转发的消息总量（根据堆积量调整） \
| kafka-console-producer.sh \
  --bootstrap-server localhost:9092 \
  --topic order-topic-backlog
```
- 注意：  
  - 若消息格式为 JSON/二进制，需确保转发时不破坏格式（避免控制台消费时的编码问题）；  
  - 可使用 `kafkacat` 工具替代自带脚本，支持更灵活的格式处理：  
    ```bash
    kafkacat -C -b localhost:9092 -t order-topic -o beginning -e | kafkacat -P -b localhost:9092 -t order-topic-backlog
    ```


#### 3. 用新消费组处理临时 Topic 的消息
```bash
# 启动专用消费者处理临时 Topic
nohup kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic order-topic-backlog \
  --group order-backlog-consumer-group \
  --max-poll-records 2000 > /dev/null 2>&1 &
```


### 五、调整生产者速率（控制消息写入速度）
若生产者发送速率远超消费能力，需临时限流：

#### 1. 查看生产者当前速率（通过监控工具）
```bash
# 查看 Topic 生产 TPS（需 Kafka 版本 ≥ 2.0）
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe \
  --topic order-topic \
  --metrics \
  --time 1000  # 采样间隔（毫秒）
```

#### 2. 在生产者端配置限流（示例：Java 生产者）
```java
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
// 限制每秒发送请求数（≈ TPS）
props.put("max.in.flight.requests.per.connection", 5);  // 每次连接最多5个未确认请求
props.put("linger.ms", 100);  // 批处理延迟，合并请求减少发送次数
props.put("batch.size", 16384);  // 批处理大小（16KB）
```


### 六、清理过期消息（释放磁盘空间）
若堆积消息中存在过期数据（如超过保留期），可调整 Topic 的消息保留策略，自动清理旧消息：
```bash
# 调整消息保留时间（单位：毫秒，如设置为1小时=3600000ms）
kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter \
  --topic order-topic \
  --config retention.ms=3600000

# 调整消息保留大小（单位：字节，如设置为10GB=10737418240字节）
kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter \
  --topic order-topic \
  --config retention.bytes=10737418240
```


### 总结
Kafka 处理消息堆积的核心命令流程：  
1. 用 `kafka-consumer-groups` 查看堆积分区和数量；  
2. 启动更多消费者实例（同组）+ 调整 `max-poll-records` 提升消费速度；  
3. 若分区不足，用 `kafka-topics --alter` 扩容分区；  
4. 必要时迁移堆积消息到临时 Topic 分流处理；  
5. 调整生产者速率和消息保留策略，避免再次堆积。  

这些命令可结合自动化脚本（如 Shell、Python）批量执行，适合大规模集群场景。
