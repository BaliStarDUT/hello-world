Redis 的持久化机制和高可用架构是其作为高性能缓存和数据库的核心保障，前者确保数据不丢失，后者解决单点故障和负载均衡问题。以下是详细解析：


### 一、Redis 持久化机制（数据持久化）
Redis 提供两种核心持久化方式，可单独使用或结合使用，目标是将内存中的数据定期保存到磁盘，避免重启后数据丢失。

#### 1. RDB（Redis Database）：快照持久化
**原理**：在指定时间间隔内，将内存中的**全量数据**生成快照（二进制文件）并写入磁盘（默认文件为 `dump.rdb`）。  
**触发方式**：  
- **自动触发**：通过配置文件 `redis.conf` 中的 `save <seconds> <changes>` 定义触发条件（如 `save 900 1` 表示 900 秒内有 1 次修改则触发）。  
- **手动触发**：执行 `save`（阻塞 Redis 主线程，不推荐）或 `bgsave`（fork 子进程执行快照，主线程不阻塞）命令。  
**执行流程**：  
1. 当触发条件满足时，Redis 调用 `bgsave` 生成子进程（`fork` 操作，复制主线程的内存页表）。  
2. 子进程遍历内存数据，生成 RDB 快照文件（期间主线程可正常处理命令，写入的数据会进入“脏页”，不影响子进程的快照）。  
3. 快照完成后，新 RDB 文件替换旧文件。  

**优点**：  
- 快照文件体积小（二进制压缩），适合备份和灾难恢复。  
- 恢复速度快（直接加载二进制文件到内存）。  
**缺点**：  
- 可能丢失最后一次快照后的所有数据（如 Redis 崩溃）。  
- `fork` 子进程时可能短暂阻塞（取决于内存大小，大内存实例阻塞时间更长）。  


#### 2. AOF（Append Only File）：日志持久化
**原理**：将所有写命令（如 `set`、`hmset`）以文本形式追加到日志文件（默认 `appendonly.aof`），重启时通过重放命令恢复数据。  
**触发方式**：  
- 开启 AOF：在 `redis.conf` 中设置 `appendonly yes`。  
- 命令同步策略：通过 `appendfsync` 配置刷盘时机（核心参数）：  
  - `always`：每个写命令立即刷盘（安全性最高，性能最差）。  
  - `everysec`：每秒批量刷盘（默认，平衡安全与性能，最多丢失 1 秒数据）。  
  - `no`：由操作系统决定刷盘时机（性能最好，安全性最差）。  

**AOF 重写（Rewrite）**：  
AOF 文件会随命令增多而膨胀，Redis 通过重写机制压缩文件：  
- 原理：遍历当前内存数据，生成“重建数据的最小命令集”（如多个 `hset` 合并为一个），替换旧 AOF 文件。  
- 触发：自动（`auto-aof-rewrite-min-size` 和 `auto-aof-rewrite-percentage` 配置）或手动执行 `bgrewriteaof`（fork 子进程执行，不阻塞主线程）。  

**优点**：  
- 数据安全性更高（丢失数据量可控，默认最多 1 秒）。  
- 日志文件是文本格式，可手动修改或恢复特定操作。  
**缺点**：  
- AOF 文件体积通常比 RDB 大，恢复速度较慢。  
- 重写过程需要额外内存和 IO 资源。  


#### 3. 持久化方案选择
- **仅用 RDB**：适合对数据一致性要求不高（如缓存），追求性能和恢复速度的场景。  
- **仅用 AOF**：适合对数据安全性要求高（如存储），可接受稍低性能的场景。  
- **RDB + AOF 结合**：重启时优先加载 AOF（数据更完整），同时保留 RDB 用于备份，平衡安全与性能（Redis 4.0+ 支持）。  


### 二、Redis 高可用架构
高可用架构的目标是：**避免单点故障（服务不可用）、实现负载均衡、保证数据一致性**。Redis 常用高可用方案包括：主从复制、哨兵（Sentinel）、集群（Cluster）。

#### 1. 主从复制（Master-Slave Replication）
**架构**：1 个主节点（Master）+ 多个从节点（Slave），主节点处理读写请求，从节点仅处理读请求并同步主节点数据。  
**核心作用**：  
- 读写分离：分担主节点的读压力（从节点可提供读服务）。  
- 数据备份：从节点是主节点的副本，主节点故障时可手动切换到从节点。  

**数据同步原理**：  
- **全量同步**：从节点首次连接主节点时，主节点生成 RDB 快照并发送给从节点，从节点加载 RDB 后，主节点再将期间的写命令同步给从节点（通过缓冲区）。  
- **增量同步**：全量同步后，主节点将后续写命令实时同步到从节点（基于偏移量 `offset` 确保数据一致）。  

**缺点**：  
- 主节点故障后需手动切换到从节点，无法自动恢复可用性。  
- 无法解决单主节点的写压力瓶颈。  


#### 2. 哨兵（Sentinel）：自动故障转移
**架构**：在主从复制基础上，增加一组哨兵进程（Sentinel），负责监控主从节点状态、自动选举新主节点、通知客户端新的主节点地址。  
**核心功能**：  
- **监控**：定期检查主从节点是否存活（发送 `PING` 命令）。  
- **自动故障转移**：若主节点宕机，哨兵通过投票选举一个从节点升级为新主节点，其他从节点切换到新主节点同步数据。  
- **配置管理**：客户端通过哨兵获取当前主节点地址（无需硬编码）。  

**工作流程**：  
1. 哨兵集群通过 `pub/sub` 机制互相通信，交换节点状态信息。  
2. 当多数哨兵（超过半数）判定主节点“主观下线”（自身检测到不可达），则标记主节点“客观下线”。  
3. 哨兵集群投票选举出 leader 哨兵，由其执行故障转移（选新主、切换从节点、通知客户端）。  

**优点**：  
- 自动处理主节点故障，实现高可用（无需人工干预）。  
- 兼容主从复制的读写分离，适合中小规模场景。  
**缺点**：  
- 仍依赖单主节点，写操作集中在主节点，无法横向扩展写能力。  


#### 3. 集群（Redis Cluster）：分布式高可用
**架构**：由多个主节点（最少 3 个）和从节点组成，每个主节点负责一部分哈希槽（共 16384 个槽），数据按 `key` 的哈希值分配到对应槽位，实现数据分片。  
**核心特性**：  
- **数据分片**：每个主节点负责 16384 个槽中的一部分（如 3 主节点各负责 ~5461 个槽），解决单节点内存和写压力瓶颈。  
- **高可用**：每个主节点至少有 1 个从节点，主节点故障时，从节点自动升级为新主节点（类似哨兵的故障转移）。  
- **客户端路由**：客户端可直接连接任意节点，若 `key` 不在当前节点负责的槽，节点会返回 `MOVED` 指令，指引客户端到正确节点。  

**数据一致性保障**：  
- 主从同步：同主从复制机制，从节点实时同步主节点数据。  
- 槽迁移：支持在线扩容/缩容，通过迁移槽位平衡数据分布（不影响服务）。  

**优点**：  
- 横向扩展：支持多主节点，分散写压力，适合大规模数据和高并发场景。  
- 自动故障转移：每个主节点的从节点可自动接替故障主节点。  
**缺点**：  
- 架构复杂，运维成本高（需管理多个节点和槽位）。  
- 跨槽操作（如 `MGET` 涉及多个槽的 `key`）需客户端处理，增加复杂度。  


### 三、高可用架构选择建议
- **中小规模场景**（读多写少，数据量不大）：**主从复制 + 哨兵**，兼顾高可用和读写分离，部署简单。  
- **大规模场景**（数据量大，写压力高）：**Redis Cluster**，通过分片扩展存储和写能力，自带高可用机制。  
- **极致性能 + 高可用**：结合哨兵/集群与持久化（RDB+AOF），确保数据不丢失且服务持续可用。  


### 总结
- **持久化**：RDB 适合备份和快速恢复，AOF 适合高数据安全性，实际中常结合使用。  
- **高可用**：主从复制解决读写分离和备份，哨兵实现自动故障转移，集群实现分布式扩展，需根据业务规模选择合适架构。


# Redis的数据分片机制
Redis 集群（Redis Cluster）通过**哈希分片（Hash Sharding）** 机制将数据分布式存储在多个节点上，核心是将 `Key` 映射到固定数量的“哈希槽（Hash Slot）”，再由集群负责管理槽位与节点的对应关系，实现数据的横向扩展。


### 一、哈希分片的核心原理
Redis 集群的哈希分片遵循以下规则：

1. **固定哈希槽数量**  
   整个集群预定义了 **16384 个哈希槽**（`0~16383`），每个槽位对应一部分数据，所有槽位共同覆盖集群的全部数据。

2. **Key 到槽位的映射**  
   对于每个 `Key`，Redis 通过 **CRC16 哈希算法**计算哈希值，再对 16384 取模，得到该 `Key` 所属的槽位：  
   ```
   槽位 = CRC16(Key) % 16384
   ```  
   例如：`Key = "user:100"` 的 CRC16 哈希值取模后可能对应槽位 `5461`。

3. **槽位与节点的映射**  
   - 每个主节点负责一部分槽位（如 3 个主节点可分别负责 `0~5460`、`5461~10922`、`10923~16383`）。  
   - 槽位与节点的映射关系存储在集群元数据中，所有节点共同维护并同步这一信息。  
   - 客户端访问 `Key` 时，会先计算槽位，再根据槽位与节点的映射，将请求路由到负责该槽位的主节点。


### 二、哈希分片的关键机制
#### 1. 槽位分配与迁移
- **初始分配**：集群创建时，可通过 `redis-cli --cluster create` 命令手动或自动分配槽位（如 3 主节点平均分配 16384 个槽）。  
- **动态迁移**：当集群扩容/缩容时，可通过 `redis-cli --cluster reshard` 命令迁移槽位（及槽位中的数据），过程如下：  
  1. 从源节点取出待迁移槽位中的所有 `Key`。  
  2. 将 `Key` 逐个迁移到目标节点（先迁移数据，再更新槽位映射）。  
  3. 迁移完成后，集群广播新的槽位映射，所有节点同步更新。  
  （迁移过程不阻塞服务，支持在线扩容）

#### 2. 客户端路由
客户端访问集群时，若连接的节点不负责目标 `Key` 的槽位，会返回 `MOVED` 重定向指令，指引客户端连接正确的节点：  
```bash
# 示例：客户端连接节点 A，请求 Key 属于节点 B 的槽位
127.0.0.1:6379> GET user:100
(error) MOVED 5461 192.168.1.2:6379  # 重定向到节点 B（192.168.1.2:6379）
```  
- 现代客户端（如 Jedis、Redisson）会自动缓存槽位映射，减少重定向次数。  
- 若槽位正在迁移（部分 `Key` 在源节点，部分在目标节点），节点会返回 `ASK` 指令，客户端需先向目标节点发送 `ASKING` 命令，再重试请求。

#### 3. 哈希标签（Hash Tag）：强制 Key 归属于同一槽位
默认情况下，每个 `Key` 独立计算槽位，但有时需要将相关 `Key` 存储在同一节点（如 `user:100:name` 和 `user:100:age`），可通过**哈希标签**实现：  
- 规则：若 `Key` 中包含 `{xxx}` 格式的子串，则仅对 `{}` 内的内容计算哈希（忽略其他部分）。  
- 示例：  
  - `Key = "user:{100}:name"` → 仅用 `100` 计算槽位。  
  - `Key = "user:{100}:age"` → 同样用 `100` 计算槽位，与上一个 `Key` 同属一个槽位。  


### 三、哈希分片的优势与局限
#### 优势
1. **横向扩展**：通过增加节点并分配槽位，可线性提升集群的存储容量和读写性能。  
2. **负载均衡**：槽位均匀分配到多个节点，避免单节点负载过高。  
3. **高可用**：每个槽位由主节点负责，从节点实时同步数据，主节点故障时从节点自动接管槽位。  

#### 局限
1. **跨槽操作限制**：涉及多个槽位的命令（如 `MGET key1 key2` 若 `key1` 和 `key2` 属于不同槽位）无法直接执行，需客户端分别请求再合并结果。  
2. **槽位迁移开销**：大规模槽位迁移可能短暂影响性能（需拷贝数据并更新映射）。  
3. **哈希倾斜风险**：若大量 `Key` 哈希后集中在少数槽位，会导致对应节点负载过高（需通过哈希标签或业务设计规避）。  


### 四、总结
Redis 集群通过“`Key` → 哈希槽 → 节点”的三层映射实现哈希分片，核心是 16384 个哈希槽的分配与管理。这一机制让 Redis 突破单节点内存和性能限制，支持海量数据和高并发场景，是分布式 Redis 的核心实现。  

实际使用中，需注意跨槽操作的限制，合理设计 `Key` 结构（如需关联数据可使用哈希标签），并通过监控工具（如 Redis Insight）确保槽位负载均衡。
